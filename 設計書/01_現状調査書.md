## 4. 実装済みの機能【事実】

| 機能 | 中身 | 主な場所 |
|---|---|---|
| チャットの読み取り（GRAVITY） | MuMu の画面の部品一覧（`dump_hierarchy`）を読む。表示先のディスプレイを毎回割り出す。監視範囲の文字、または音声ルームのチャット欄(`rvMessages`)の枠で絞る | `_extract_chat_texts`、`_update_target_display`、`find_chat_list_bounds` |
| チャット欄を意味で読む | 1行ずつ「発言（名前・本文）／お知らせ（参加・いいね・マイク・ルーム名の変更）／アナウンス／不明」に分ける | `parse_chat_rows`、`chat_notice_kind` |
| キーワード自動返信 | セット・ペア・有効無効、ペアごとの「対象」、返信ワードの `{名前}`、クールダウン、同じ行への二重返信の防止（見えている間だけ覚える）、自分の発言の除外 | `_run_monitor`、`match_keyword_rows`、`_select_pending_replies` |
| チャットへの書き込み | 入力欄(`etText`)を押す → 貼り付け（失敗したら直接入力）→ 入れた文字を読み戻して確かめる → 送るボタン（無ければ Enter） | `_execute_reply`、`_send_reply` |
| 手入力の送信 | 送信待ち（最大20件）、自分の発言として覚える | `enqueue_manual_texts` |
| 音声合成 | VOICEVOX と AivisSpeech。話者は「エンジン名:話者ID」の文字列で選ぶ。合成結果を最大40件まで覚えて再利用。エンジンの自動起動 | `synthesize_voice_wav`、`TTS_ENGINES` |
| 読み上げ | 待ち行列（最大20件・1件200文字まで）→ 専用スレッドが合成→再生。入口は手入力・クリップボード監視・スマホ | `request_speech`、`_speech_worker` |
| 再生 | 選んだ出力デバイス（VB-CABLE なども可）か既定のデバイスへ。音量。マイクの音を出力先へ流す機能 | `_play_wav_bytes`、`build_audio_input_section` |
| スマホ連携 | 同じ Wi-Fi のスマホから文字を受け取って読み上げる。既定はOFF、暗証番号、5回失敗で30秒受け付けない、HTTPS | `PhoneBridgeServer` |
| GRAVITY のタスク・ルーレット | 開いているアカウントを順にこなす。押してよい画面・押してはいけないボタンの守り、知らない画面ですぐ止める | `GravityTaskWorker` |
| タイマー・アラーム | VOICEVOX の声などで知らせる | `build_timer_tab` |
| ログ | 画面のログ、DB の `logs` 表（最大5,000行、第三者の名前を伏せる）、`error_log.txt` | `mask_screen_text`、`write_error_log` |
| 自動更新 | GitHub Releases から取得し、閉じるときに差し替え（`robocopy /E`、`app_data.db` と `error_log.txt` は除外） | `UpdateManager` |
| テスト | 11本（実機なし）＋実機テスト1本（`--live` を付けたときだけ動く）。伏せ字にした実物の画面で検証 | `tests/` |

## 6. 既知の問題・暫定実装・設計上の課題【事実】

| # | 内容 | 影響 |
|---|---|---|
| P1 | 本体が約12,400行の1ファイル。画面（`App`）の中に音声合成・再生・エンジン切り替えのメソッドがある | 画面を作らないと音声の処理をテストできない。エージェントを足す場所が無い |
| P2 | 音声エンジンの切り替えが `if` の分岐（2エンジン固定）。話者の選び方は「エンジン名:ID」の文字列 | 3つ目（VOICEPEAK など）を足すと分岐が増える |
| P3 | 再生は `stream.write()` のあと音の長さだけ `sleep` する。止める・割り込む手段が無い | AIの発言を途中で止められない |
| P4 | 設定は `settings` 表に平文で保存（スマホ連携の暗証番号も平文） | APIキーを同じやり方で保存してはいけない |
| P5 | 自動返信の判断が監視ループ（`_run_monitor`）の中に直接書かれている | チャットアプリ固有の処理と判断が分かれていない。エージェントの判断を足すと、さらに長くなる |
| P6 | チャットの行の目印は文字列（発言は「名前: 本文」）。同じ人が同じ文を2回言うと区別できない | 出来事（イベント）の重複判定に限界がある |
| P7 | スレッドの止め方がそれぞれ別（`is_running` など）。全体をまとめて止める仕組みが無い | 緊急停止・後片付けを足すとき、まとめ役が要る |
| P8 | ログは画面・DB・`error_log.txt` の3系統で、形が揃っていない | 判断・API・費用の記録を足すとき、置き場所を決める必要がある |
| P9 | 監視範囲がウィンドウの位置に依存する（意図した仕様。音声ルームはチャット欄の枠で自動にもできる） | ― |
| P10 | GRAVITY は公式の API が無い前提で、画面を読んで操作している【公式APIの有無は未確認】 | 部品の名前が変わると読めなくなる |
| P11 | GRAVITY の利用規約での自動化の扱い【未確認】 | 自動で発言する機能は、アカウントへの影響がありうる |

## 7. 既存設計の評価

**守るべき良い点**（壊さない・まねる）

- **安全側に倒す作りが徹底している**: 押してよい画面の一覧、押してはいけないボタンの守り、知らない画面ですぐ止める、人に届く操作は本人の了解をとってから。エージェントの「ツール実行」と「人に聞こえる発言」も同じ考え方にする
- **実物を伏せ字にしたテスト用の画面で検証する**: エージェントの「チャット→判断」のテストにもそのまま使える
- **スレッドが落ちても止まらない作り**: 読み上げのスレッドは1件の失敗で止まらない。画面への受け渡しは伝言板(`_post_to_ui`)だけ
- **待ち行列に上限がある**: 読み上げ20件、手入力20件、返信済みの記録300件、合成結果40件
- **設定を変えても既存の動きが変わらない移し替え**（例: キーワードの「対象」は既存ペアを「今まで通り」にした）

**改める候補**（エージェントのために必要な分だけ）

- 音声合成・再生を画面から切り離す（P1・P2・P3）
- チャットの出来事を、監視ループから**イベントとして外へ渡す口**を作る（P5）
- 機密情報の保存方法を足す（P4）
- 全体の停止をまとめる役を足す（P7）

**変えなくてよい部分**

- GRAVITY の読み取り・送信・タスクの守り、キーワード自動返信、スマホ連携、自動更新、タイマー
- 画面の構成（タブを1つ足す、設定タブに区画を足す、で足りる）

## 8. 関連プロジェクト「ひといき」（別フォルダ）【事実】

キャラクターの性格・口調を決めて Gemini と会話し、返事を読み上げる Windows アプリ（Electron、JavaScript）。git 管理外。

| 項目 | 内容 |
|---|---|
| AI API | Gemini（REST。`https://generativelanguage.googleapis.com/v1beta`、`generateContent`）。APIキーは **`x-goog-api-key` ヘッダーで渡し、URL に入れない** |
| 使っているモデル名（コード上） | `gemini-3.1-flash-lite`、`gemini-3.8-flash`、`gemini-3.1-flash-tts-preview`（現在も提供されているかは【未確認】） |
| APIキーの保存 | Electron の `safeStorage`（Windows では DPAPI）で暗号化して `settings.json` に保存。保存しない選択もできる |
| 守り | 通信してよいパスの一覧で縛る、1回の送信は128KBまで、60秒で打ち切る、会話は直近10往復（20,000文字相当）まで送る |
| 音声 | Gemini の音声生成、Windows の音声。VOICEVOX・AivisSpeech は使っていない |
| チャットアプリ連携 | 無い |
| テスト | 外部と通信しない模擬応答のテスト |

**評価**: 「APIキーの守り方」「送る会話の上限」「通信先の一覧で縛る」は、そのまま設計の参考になる。
コードは JavaScript なので、Python のグラ補助ツールへは**考え方だけ**を持ち込む（コードの移植はしない）。
