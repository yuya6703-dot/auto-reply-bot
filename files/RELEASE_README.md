# リリース手順（自動ビルド＆自動リリース）

`.github/workflows/release.yml` を設定済みなら、以下の3手順だけで新バージョンを配布できます。
手元でのexeビルドやGitHub Releaseページの手作業は不要です。

## 手順

1. **コード内のバージョンを上げる**

   `auto_reply_app.py` の冒頭にある以下の行を、新しいバージョン番号に書き換える。

   ```python
   APP_VERSION = "1.1.0"
   ```

2. **変更をコミットしてpush**

   ```bash
   git add auto_reply_app.py
   git commit -m "v1.1.0: 変更内容の説明"
   git push
   ```

3. **バージョンと同じ番号でタグを作り、push**

   ```bash
   git tag v1.1.0
   git push origin v1.1.0
   ```

   ※ タグ名の数字部分（`v1.1.0` の `1.1.0`）は、手順1の `APP_VERSION` と必ず一致させてください。
   ずれるとアプリ側のアップデート判定がおかしくなります。

## 何が自動で起きるか

タグをpushすると、GitHub Actions が自動的に：

1. Windows環境でPythonと依存パッケージをセットアップ
2. PyInstallerで `自動送信ボット.spec` を使い、`dist/自動送信ボット` フォルダ一式をビルド
   （`--onedir` 方式、exe＋依存ファイル）
3. そのフォルダの中身を `auto_reply_app.zip` にまとめる
4. zipを添付した新しいGitHub Releaseを、タグ名と同じバージョンで自動作成
5. リリースノートも、前回タグからのコミット履歴をもとに自動生成

### ⚠️ exe名について（重要）

アプリの自動更新は、**今動いているexeと同じ名前のexe** をzipの中から探して差し替えます。
そのため、ビルドされるexe名が配布中のexe名（`自動送信ボット.exe`）と食い違うと、
更新が必ず「zip内に見つかりません」で失敗します。

これを防ぐため、CIは手元と同じ `自動送信ボット.spec` を使ってビルドしています。
exe名を変えたい場合は、specファイルの `name=` を書き換えてください
（`.github/workflows/release.yml` 側にexe名を直接書かないこと）。

⚠️ exe名を変更した場合、**変更後のバージョンから先** でないと自動更新は成功しません。
配布済みの旧バージョンは古い名前のexeを探し続けるためです。
名前を変える場合は、利用者に手動での入れ替えを案内してください。

進捗は、GitHubリポジトリの「Actions」タブから確認できます（数分かかります）。
完了すると「Releases」ページに新しいzipが並び、アプリ内の「🔄 アップデート確認」ボタンや
起動時の自動チェックで検知されるようになります。

## アップデート適用時の動作（アプリ内）

- 新しいzipをダウンロードし、一時フォルダに展開
- 展開したフォルダの中から新しいexeを探し、そのフォルダを新しいアプリ本体として使用
- 更新前に、現在のアプリフォルダ一式を `%USERPROFILE%\AutoReplyTool_Backups` にzipでバックアップ
- `app_data.db`（キーワード設定・各種設定）と `error_log.txt` は上書き・削除の対象外（ユーザーデータは保持されます）
- アプリを終了し、外部batファイルがファイルの差し替え→再起動までを自動で行う

## 初回セットアップで確認すること

- このフォルダ（`auto_reply_app.py` がある階層）が git リポジトリのルートになっていること。
  ワークフローは `.github/workflows/release.yml` に置く必要があり、
  この場所以外だと GitHub Actions は一切動きません。
- リポジトリの Settings → Actions → General で、
  "Workflow permissions" が "Read and write permissions" になっていること
  （Release作成に書き込み権限が必要なため）
- 初めてzip方式でリリースする際は、実際にダウンロード→展開→差し替えの流れが
  問題なく動くか、一度手元で確認することをおすすめします
